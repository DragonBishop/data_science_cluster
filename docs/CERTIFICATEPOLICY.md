# Certificate Policy

## The Rules

1. Trust a certificate only when it identifies the service or workload you expected, is valid for the connection, and can be verified using the intended CA.
2. Give each issuer only the signing access it needs.
3. The shared OpenBao signing profile limits certificate names, uses and lifetimes.
4. Trust bundles distribute public CA certificates, never private keys.
5. Renew service and workload certificates automatically before expiry. Distribute replacement CA trust before switching issuers.

This single-node cluster trusts its human administrator and its configured Flux and cert-manager controllers. Kubernetes permissions control who may create certificate resources or edit issuers. A ClusterIssuer is available across namespaces; choosing a profile is not a namespace access boundary.

## Trust Ownership

| Consumer | Trust source |
| --- | --- |
| OpenTofu, cert-manager and SPIRE connecting to OpenBao | `openbao-local-ca-secret`, distributed as `openbao-ca-bundle` |
| Gateway, SeaweedFS S3, Results API and Hubble clients | OpenBao's service-PKI root, distributed as `openbao-root-ca` or carried in their TLS Secret |
| PostgreSQL server verification and replication | Dedicated `postgres-ca` |
| PostgreSQL SVID login | `postgres-client-ca`, containing the SPIRE signing root and PostgreSQL replication CA |
| Flux controller mTLS and workload identity consumers | SPIRE's workload API trust bundle |
| SeaweedFS internal HTTPS/gRPC | SeaweedFS's chart-owned CA |

Keep the listener CA, service PKI, PostgreSQL CA and SeaweedFS CA distinct. DNS name constraints do not restrict SPIFFE URI identities. Editing leaf profiles does not replace CA roots or revoke certificates already issued.

## Signing Profiles

| Issuer | Signing authority | Names and usages | Lifetime |
| --- | --- | --- | --- |
| `openbao-pki-issuer` | OpenBao `pki_int/sign/internal-server` | Server/client authentication for `${INTERNAL_DOMAIN}`, Kubernetes service names under `svc.cluster.local`, Hubble's `hubble-grpc.cilium.io`/`hubble-relay.cilium.io` families, and SeaweedFS S3's short aliases/localhost. No IP or URI SANs. | Up to 30 days |
| `openbao-ca-issuer` | OpenBao's local listener CA | OpenBao's service aliases and loopback; server authentication. | `LOCAL_CA_CERT_DURATION` |
| `postgres-ca-issuer` | Dedicated PostgreSQL CA | PostgreSQL service/Gateway names and IPs for server authentication; `streaming_replica` for replication client authentication. | `OPENBAO_PKI_CERT_DURATION` |
| SeaweedFS's namespaced `seaweedfs-ca-issuer` | Chart-owned SeaweedFS CA | Internal HTTPS/gRPC service and client certificates generated by the chart. | `LOCAL_CA_CERT_DURATION` |
| SPIRE upstream authority | OpenBao `pki/root/sign-intermediate` | SPIRE intermediates and workload identities in trust domain `cluster.internal`. | `SPIRE_CA_TTL` for intermediates |

OpenBao enforces the shared profile's DNS names, SAN types and lifetime. Wildcard certificates remain permitted for the Gateway and Hubble. The CA issuers use their configured CA directly; OpenBao's leaf-role restrictions do not apply to those issuers.

Hubble's Cilium chart uses one issuer for three certificates: its server requests both server and client authentication, its Relay client requests client authentication, and its Relay server requests server authentication. The shared OpenBao role retains both usages; ordinary service certificates can also carry client authentication. Workload identity and application permissions remain governed by SPIRE and the receiving service's authentication rules.

The `internal-server` profile takes its Gateway domain from `cluster-config` through Ansible's OpenTofu inputs. Its short names are the SeaweedFS S3 aliases already used by consumers. Adding an ordinary service FQDN under `svc.cluster.local` does not require another signing role.

## Adding a Service Certificate

Declare the name the client actually connects to and choose the server issuer:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-tls
  namespace: example
spec:
  secretName: example-tls
  dnsNames:
    - example.example.svc.cluster.local
  duration: ${OPENBAO_PKI_CERT_DURATION}
  renewBefore: ${OPENBAO_PKI_CERT_RENEW_BEFORE}
  privateKey:
    algorithm: ${CERT_KEY_ALGORITHM}
    size: ${CERT_KEY_SIZE}
  issuerRef:
    name: openbao-pki-issuer
    kind: ClusterIssuer
```

Use the existing Gateway wildcard for HTTPS routes. Use SPIRE for workload identities where supported; Hubble continues to use its chart-managed certificates and the shared issuer.

[cert-manager defaults](https://cert-manager.io/docs/usage/certificate/#x509-key-usages-and-extended-key-usages) request digital signature, key encipherment and server authentication. The signing role determines the issued certificate's permitted capabilities; the request's usages alone do not restrict the signing authority.

## Sources and Operations

OpenBao's leaf profile and issuer authentication live in [`terraform/openbao/pki.tf`](../terraform/openbao/pki.tf) and [`kubernetes-auth.tf`](../terraform/openbao/kubernetes-auth.tf). The shared ClusterIssuer lives in [`openbao-issuers.yaml`](../infrastructure/openbao/openbao-issuers.yaml); Ansible uses that same source during a clean install. Hubble's chart issuer is configured in [`hubble-values.yaml`](../infrastructure/hubble/hubble-values.yaml). Its authentication follows [cert-manager's Vault pattern](https://cert-manager.io/docs/configuration/vault/).

Apply profile changes through the existing OpenTofu provisioning path. cert-manager renews certificates through the shared issuer; issued certificates keep their validity until expiry or deliberate renewal. Confirm that required names still issue and consumers can connect after a profile change.

See [Access Policy](ACCESSPOLICY.md) for permissions, [Network Policy](NETWORKPOLICY.md) for reachability, and [Verification](VERIFICATION.md) for operator checks.
